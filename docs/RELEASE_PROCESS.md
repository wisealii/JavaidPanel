# سیاست انتشار و آرشیو نسخه‌های JavaidPanel

هدف: ریپازیتوری GitHub باید برای **هر نسخه قابل ردیابی** شامل شرح امکانات، اصلاحات، تست‌ها، محدودیت‌ها و لینک واقعی Commit/PR باشد؛ بدون ساختن سابقهٔ انتشار جعلی.

## منابع اصلی حقیقت

1. `VERSION`: نسخهٔ فعلی سورس؛ فقط در صورت تغییر واقعیِ موفق افزایش یابد.
2. `CHANGELOG.md`: هر نسخه یک بخش با قابلیت‌های افزوده/اصلاح‌شده، تست‌ها و موارد تأییدنشده.
3. `docs/VERSION_ARCHIVE.md`: فهرست و شرح نسخه‌های تاریخی، تولیدشده از CHANGELOG.
4. `docs/CURRENT_FEATURES.json`: امکانات واقعاً موجود و شواهد سورس.
5. `docs/DEVELOPMENT_PROGRESS.json`: در صورت ایجاد، وضعیت اجرای دوره‌ای و کارهای باقی‌مانده؛ هیچ‌گاه جایگزین شواهد CI نمی‌شود.
6. `docs/RELEASE_READINESS.md`: معیارهای عملی نصب VPS و موارد مسدودکننده.

## چرخه انتشار هر تغییر

1. آخرین `main` و `VERSION` و CI را بخوان؛ تکرار یا هم‌پوشانی PRها را بررسی کن.
2. مشکل P0 یا P1 مربوط به قابلیت موجود را با شواهد پیدا کن.
3. شاخه مستقل بساز؛ کد و تست رگرسیون مرتبط را پیاده‌سازی کن.
4. با تغییر واقعی و موفق، نسخه `-dev` را افزایش بده و `install.sh` و README badge را با آن هماهنگ کن.
5. یک ورودی جدید در ابتدای `CHANGELOG.md` بنویس: **قابلیت‌ها، اصلاحات، تست‌های اجراشده، محدودیت‌ها و مسیر ارتقا/بازگشت**.
6. `python3 tools/version-archive.py` را اجرا کن تا آرشیو نسخه‌ها بازسازی شود.
7. `python3 tools/version-archive.py --check` و تمام تست‌های مرتبط را اجرا کن.
8. Pull Request بساز، CI را بررسی کن و فقط با مجوز لازم و CI سبز Merge کن.
9. در گزارش فارسی لینک واقعی PR و Commit، نسخه قبلی/جدید و نتیجه CI را درج کن.
10. در نوبت بعدی از آخرین `main` ادامه بده.

## Git tag و GitHub Release

- تاریخچه `CHANGELOG.md` را **با تگ GitHub اشتباه نگیر**. نسخه‌های قدیمی ممکن است هرگز تگ یا بستهٔ منتشرشده نداشته باشند.
- ایجاد تگ تاریخی روی Commit حدسی ممنوع است. تگ فقط روی Commit واقعی و تأییدشده، با بررسی سازگاری `VERSION` ساخته شود.
- برای هر نسخه‌ای که واقعاً قرار است به‌عنوان **GitHub Release** عرضه شود، عنوان، خلاصه تغییرات، محدودیت‌ها، هش دارایی‌های قابل دانلود و لینک واقعی ارائه کن.
- برای `-dev` از وضعیت **pre-release** استفاده کن؛ آن را Stable یا Production Ready معرفی نکن.
- قبل از انتشار نهایی، `python3 tools/release-readiness.py --strict` و تست‌های واقعی VPS باید موفق باشند.
- نصب از `main` یک نسخه متغیر است؛ برای بازتولید نصب باید Commit یا تگ تأییدشده را پین کرد. هیچ دستور نصب از تگ موجودنبوده ننویس.
- اگر ابزار یا مجوز ساخت Release موجود نیست، PR و مستندات را منتشر کن و صادقانه بنویس GitHub Release هنوز ساخته نشده است.

## قالب یادداشت نسخه

```markdown
## X.Y.Z-dev — عنوان تغییر
- Features: چه قابلیت موجودی واقعاً تکمیل یا اصلاح شد.
- Fixes: مشکل اصلی و اثر آن.
- Tests: تست‌های اجراشده و نتیجهٔ واقعی.
- Compatibility: مهاجرت/بازگشت/تأثیر بر نصب قبلی.
- Limitations: تست VPS، SSL، VPN، restore و موارد انجام‌نشده.
```

## کنترل کیفیت آرشیو

`python3 tools/version-archive.py --check` در CI باید ناموفق شود اگر `VERSION` با نخستین عنوان CHANGELOG هماهنگ نیست یا آرشیو بازتولیدپذیر نیست. موارد تکراری تاریخی مانند دو ورودی `1.1.108-dev` **حفظ و آشکار** می‌شوند؛ تا وقتی Commitهای واقعی بررسی نشده‌اند، ادغام یا بازنویسی تاریخی ممنوع است.
