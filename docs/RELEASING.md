# سیاست نسخه‌بندی، آرشیو و انتشار JavaidPanel

## قرارداد نسخه

- فایل `VERSION` مرجع نسخه *سورس جاری* است. نسخه‌های آزمایشی تا آزمون واقعی VPS پسوند `-dev` دارند.
- هر تغییر معنادار و تست‌شده می‌تواند نسخه توسعه‌ای بعدی باشد. اصلاح مستندات صرفاً در صورت نیاز به انتشار نسخه جدید انجام شود.
- آرشیو تاریخی در `docs/versions.json` و `docs/releases/` نگهداری می‌شود. کاتالوگ `docs/CURRENT_FEATURES.json` وضعیت امکانات *موجود* است، نه امکانات ویژه هر نسخه.
- وجود Archive Markdown با GitHub Tag، GitHub Release یا بسته اجرایی هم‌ارز نیست.

## مراحل اجباری هر نسخه

1. وضعیت شاخه `main`، آخرین Commit، VERSION، CHANGELOG و آرشیو را بخوانید.
2. مشکل واقعی P0/P1 را رفع و برای آن تست واحد و رگرسیون اضافه کنید.
3. در `CHANGELOG.md` یک heading مستقل درج کنید. اگر در یک نسخه چند PR وجود دارد، تغییرات باید زیر همان heading واحد مستند شوند.
4. `VERSION`، متغیر `VERSION` در `install.sh`، badge/readme، `docs/CURRENT_FEATURES.json`، `docs/versions.json`، `docs/VERSIONS.md` و فایل آرشیو را هماهنگ کنید.
5. برای هر قابلیت جدید در پرونده نسخه، وضعیت تست واقعی و موانع را صریح بنویسید.
6. اجرا کنید:

```bash
python3 tools/verify-version-archive.py
python3 -m unittest discover -s tests -p 'test_version_archive.py' -v
bash install.sh --self-test
python3 tools/release-readiness.py --json
```

7. از یک Pull Request با توضیح تغییر و نتیجه آزمون GitHub Actions استفاده کنید؛ پس از موفقیت CI و بازبینی، ادغام کنید.
8. **Git Tag و GitHub Release واقعی فقط پس از ادغام**: Tag با نام `vX.Y.Z-dev` را روی Commit ادغام‌شده ایجاد کنید و Release را برای همان Tag به عنوان **prerelease** تنظیم کنید. اگر ابزار انتشار یا مجوز موجود نیست، Tag/Release را *منتشرشده* ننامید. اجرای این مرحله خودکار و بدون قابلیت مدیریت تگ در اتصال فعلی تضمین نشده است.
9. ابتدا صحت Tag و Release ایجادشده را مستقل بررسی کنید و سپس metadata را به‌روز کنید. از ساخت Tag تاریخچه قدیمی روی Commit نامعلوم جداً خودداری کنید.

## معیار کنترل کیفیت

- افزایش شماره نسخه بدون تغییر واقعی و آزمون معتبر ممنوع است.
- فهرست ویژگی‌های هر نسخه نباید ادعای عملکردی تأییدنشده داشته باشد.
- انتشار نسخه توسعه‌ای با نتیجه CI سبز همچنان به معنی **VPS-ready** نیست.
- هر مانع مهم (عدم دسترسی به VPS، SSL واقعی، migration، secret، ادغام auth) باید در پرونده نسخه و گزارش ساعتی ثبت شود.
- حفظ GPL/attribution در `LICENSE` و `SOURCES.md` اجباری است.

## شواهد نسخه‌های قدیمی

نسخه‌های 1.1.102-dev تا 1.1.111-dev از روی CHANGELOG و Pull Requestهای شناخته‌شده فهرست شده‌اند. همه آن‌ها آرشیو توضیحی هستند؛ Git Tags و GitHub Releases متناظر در این مرحله **تأیید نشده‌اند** و هیچ باینری قدیمی بازسازی یا جعل نشده است.
