## روش انتشار نسخه جدید

1. نسخه بعدی فقط پس از تغییر واقعی کد و نتیجه موفق CI انتخاب می‌شود. نسخه را هم‌زمان در `VERSION`، `install.sh`، `README.md`، `docs/CURRENT_FEATURES.json` و `docs/versions.json` به‌روزرسانی کنید.
2. یک رکورد مستقل در `docs/versions.json` و یک فایل `docs/releases/X.Y.Z-dev.md` بسازید و **قابلیت‌ها، تغییرات، محدودیت‌ها و شواهد تست واقعی** را ثبت کنید.
3. به `CHANGELOG.md` یک بخش جدید اضافه کنید و در GitHub Pull Request مستند ایجاد کنید.
4. CI از طریق `tools/verify-version-archive.py` یکپارچگی رکوردها، شماره نسخه و مسیرها را بررسی می‌کند.
5. پس از Merge، برای انتشار GitHub Release واقعی باید در صورت وجود مجوز، Tag تغییرناپذیر روی **همان Commit مشخص** ایجاد و Release مطابق همان Tag منتشر شود. قبل از آن هیچ مدخلی را به‌عنوان Tag یا Release موجود نمایش ندهید.
6. Tag/Release واقعی را در رکورد نسخه با شواهد قابل بررسی ثبت کنید؛ برای نسخه‌های قدیمی به‌طور خودکار و بدون بازبینی Tag نسازید.
7. نسخه توسعه‌ای `-dev` را نباید «stable»، «production-ready» یا تأییدشده روی VPS نام‌گذاری کرد.

**تمایز مهم:** فایل Markdown هر نسخه آرشیو *اطلاعات توسعه* است، نه snapshot غیرقابل‌تغییر Git. برای بازیابی کد دقیق نسخه‌ها به Git Tag تأییدشده روی Commit متناظر نیاز است.
